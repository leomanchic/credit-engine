# Журнал проверки ТЗ и решений

Источник: `../credit_engine_spec.docx`, версия 2.0 от 2026-10-21. Документ прочитан полностью, включая таблицы, разделы 1–21 и приложения А/Б. Оригинал не изменён. `spec_extracted.txt` сохраняет порядок абзацев и таблиц для проверки реализации. Папка первоначально содержала только DOCX; Git и код сайта отсутствовали.

Полное окно обычной автоматической ветки: `[as_of_date − 12 календарных месяцев, as_of_date)`. Включённые границы для 2026-10-21: 2025-10-21…2026-10-20. | Тесты A01 в `tests/test_properties.py` |

Первоначальный вопрос A01: §6 требует покрытие 12 месяцев, но не определяет маршрут завершённого ответа с коротким окном. Пример: COMPLETE с 2026-04-21 по 2026-10-20 при расчётной дате 2026-10-21. Рассматривались WAITING_CHECKS и InputValidationError; пользователь выбрал первый вариант.

Реализация A01: корректный частичный COMPLETE даёт `HISTORY_UNAVAILABLE` с `required_window_start`, `required_window_end`, `actual_window_start`, `actual_window_end` и действием `REQUEST_FULL_HISTORY`. При остальных достаточных входах результат — WAITING_CHECKS; `score_total=null`, автоматических предложений нет. Проверка сохраняет исходный COMPLETE, входы не меняются. Backend выполняет запрос и ожидание. Приоритет неактивной компании и общий порядок NEEDS_INFO → WAITING_CHECKS → MANUAL_REVIEW сохраняются.

Полное окно с кредитами только в последние шесть месяцев достаточно: даты фактической активности в DTO не вводятся и из покрытия не выводятся. Подтверждённое отсутствие истории за полное окно получает NO_HISTORY. Молодая компания остаётся в маршруте SHORT_OPERATING_HISTORY: проверка полноты годового покрытия обычной автоматической ветки не требует сведений до начала её деятельности. Обратный интервал `window_start > window_end` остаётся InputValidationError.

## B — технические решения без изменения правил ТЗ

- Python 3.12.14, Pydantic 2.12.3, src-layout, setuptools. Окружения разработки и проверки wheel изолированы. Полные версии зависимостей фиксируются в `requirements.lock`.
- Локальная точность демонстрационной политики — 50 знаков; Decimal-контекст создаётся заново и не зависит от точности, rounding или traps вызывающего кода.
- Входы заморожены; списки хранятся как tuple. `evaluate` повторно валидирует даже DTO, исключая обход через `model_construct`/`model_copy`. Публичный Python-вызов дополнительно принимает dict.
- DTO вложенного результата: поля компонентов `payment/history/stability/tenure/base_score`; вклад актива `accepted_value`; `required_route` поясняет неопределённость актива, не задавая автоматически статус всей заявки. JSON Schema фиксирует этот выбор.
- Все денежные значения JSON имеют два знака, коэффициенты — обычную десятичную запись без лишних нулей и экспоненты. Отрицательный ноль нормализуется в ноль. Денежные результаты могут быть больше NUMERIC(18,2), поскольку ограничение из §4 относится к входам.
- В канонизации сортируются только неупорядоченные коллекции. Порядок предложений сохраняется. Наборы балльных корзин должны поступать в проверяемом порядке порогов.
- При сдвиге 29 февраля на 12 календарных месяцев назад используется последний день февраля предыдущего года. Это календарная техническая конвенция A01; месяцы финансового окна всегда полные календарные.
- Поддерживаемый диапазон настраиваемой политики ограничен явно: сроки 1–120 месяцев, ставка 0–1, коэффициенты DSCR/покрытия до 100, не более 12 дробных знаков, Decimal precision 34–200, 1–3 предложения. Валидатор отклоняет неохваченные и немонотонные корзины, неизвестные режимы и противоречивые диапазоны. Это границы реализации, не новая кредитная политика.
- Неполученные поля в завершённых положительных оценках — ошибка контракта; `null` финансовой статьи и MISSING — бизнес-состояния. Отрицательно проверенный актив не обязан иметь ненужную оценку.
- Пояснение `AMOUNT_STEP_LIMIT` различает отсутствие допустимой уменьшенной суммы на настраиваемой сетке и плохой скор. Дополнительное действие `OPTIONAL_COLLATERAL_ASSESSMENT` появляется только при уже доступном предложении, если неопределённый дополнительный актив способен увеличить допустимую сумму; оно не блокирует предложение.
- Форматы денег, коэффициентов и дат используют ASCII-цифры. Расчётная дата должна позволять представить предыдущие 12 месяцев (`as_of_date >= 0002-01-01`). CLI явно задаёт UTF-8 для потоков, включая изолированный Python на Windows.

## C — редакционные замечания и независимая сверка

- В запросе указан путь `docs/credit_engine_spec.docx`; фактический файл лежит в корне рабочей папки. Использован найденный оригинал, без переименования или изменения.
- Слитные фрагменты вроде «DSCR1.30», «раздела17» и «устойчивость25» трактуются по таблицам с теми же числами.
- Числовых противоречий в §17 не обнаружено. Независимый скрипт `verify_reference_calculations.py` использует точность 60 и эквивалентную формулу с положительной степенью; совпали все шесть строк, три денежных лимита и оба залоговых примера. Ожидания тестов не получены из `evaluate`.
