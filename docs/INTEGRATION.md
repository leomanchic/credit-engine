# Подключение к Python backend

Библиотека готовит рекомендацию для одной сохранённой ревизии. Этот документ описывает границу подключения; наличие адаптера не подтверждает интеграцию с реальным сайтом. Исходников сайта в поставленной папке нет.

## Вызов и сохранение

1. Backend аутентифицирует действие пользователя и получает сохранённую актуальную ревизию из БД.
2. Из защищённого хранилища загружаются checks той же заявки и ревизии. Пользовательский HTTP-body не может назначать `COMPLETE`, `BANK_OPERATOR` или подтверждения.
3. Загружается закреплённая политика. Содержание сверяется с неизменяемым соответствием `policy_version → policy_hash`.
4. Выполняется `evaluate(snapshot, checks, policy)`; канонический результат сохраняется вместе с ревизией, `processing_id`, hash политики и версией алгоритма.
5. В одной транзакции backend повторно сверяет актуальность ревизии и processing_id, сохраняет решение и публикует разрешённые предложения. Реальные `offer_id` создаёт backend.
6. Принятие предложения транзакционно проверяет актуальность сохранённой ревизии, политики, проверок и состояния предложения. Конфликт не должен принять старое предложение.

```python
from credit_engine import evaluate, canonical_json
from credit_engine.errors import InputValidationError, PolicyValidationError

# snapshot, trusted_checks и pinned_policy получены сервером вне evaluate.
try:
    result = evaluate(snapshot, trusted_checks, pinned_policy)
except PolicyValidationError as error:
    # Ошибка конфигурации сервера: HTTP 500 и технический журнал.
    raise
except InputValidationError as error:
    # HTTP 422, безопасный error.to_dict().
    raise
else:
    internal_json = canonical_json(result)
    # Транзакционная проверка актуальности и сохранение реализуются вашим backend.
```

Исполнимый пример реального вызова: `examples/backend_adapter.py`. После установки пакета:

```powershell
.\.venv\Scripts\python.exe examples/backend_adapter.py --case F01
.\.venv\Scripts\python.exe examples/backend_adapter.py --case F02
.\.venv\Scripts\python.exe examples/backend_adapter.py --case F04b
```

В примере файловые синтетические fixtures заменяют БД исключительно для локальной демонстрации. `client_view` применяет явный список публичных полей и исключает сообщения/действия с `audience=BANK`. Полный внутренний результат передавать клиенту напрямую нельзя. `candidate_key` — детерминированный ключ расчёта, а не сохранённый `offer_id`.

## Обработка рекомендаций

| Рекомендация | Действие backend |
|---|---|
| OFFERED | Сохранить и публиковать только рассчитанные AUTO_ELIGIBLE offers при актуальной ревизии |
| NEEDS_INFO | Показать точные клиентские requested_fields и действия; сохранить новую ревизию после изменений |
| WAITING_CHECKS | Организовать ожидание/повтор проверки; для REQUEST_FULL_HISTORY запросить нужное годовое окно |
| MANUAL_REVIEW | Передать сотруднику. REVIEW-кандидат публикуется только с решением и аудитом; ранний ручной статус без кандидата сам по себе не создаёт предложения |
| DECLINED | Сохранить рекомендацию и разрешённые для клиента причины; не маскировать под техническую ошибку |

Изменение документа, принятой оценки, доходов, долга, суммы или срока означает новую ревизию и повторный расчёт. Нельзя превращать старое `monthly_cash_flow` в 12 одинаковых исторических месяцев. Отдельный нормализатор исключает внутренние переводы, кредиты и вложения владельца; ядро получает уже очищенные подтверждённые месяцы.

`MANUAL_RECOVERY` для IP требует защищённого решения сотрудника, его ссылки и дат. Это чистая оценка взыскания. Клиентская стоимость, флаг или выбранный source_type не заменяют подтверждение.

## Обязательные интеграционные проверки

Все проверки ниже требуют настоящего backend и пока не выполнены:

- Три сквозных демонстрации: F01 — исходное предложение; F02 — меньшая сумма; F04 → F04b — экспертная оценка IP, новая ревизия и повторный расчёт.
- Внутренний перевод не увеличивает нормализованный поток; статьи расходов и доход актива не учитываются дважды.
- Новый документ того же физического объекта не создаёт второе обеспечение даже после изменения клиентского ID; нормализуется object_key.
- Клиент не подменяет checks, источник, payload или ссылку на решение сотрудника.
- Технический ERROR внешнего провайдера приводит к WAITING_CHECKS; частичный COMPLETE БКИ инициирует REQUEST_FULL_HISTORY с нужными границами.
- Новая ревизия или processing_id не допускают публикации запоздалого результата; принятие старого предложения возвращает конфликт, например HTTP 409.
- Изменение содержания той же версии политики обнаруживается серверным реестром hashes.
- Сообщения BANK отсутствуют в клиентском HTTP-ответе; оператор видит внутренние причины и журнал.
- Одобрение REVIEW не обходит DSCR, залог, продуктовые лимиты и свежесть проверок; сохраняются автор, основание и время действия.

До прохождения этих проверок статус модуля — «проверено локально, требует интеграционной проверки».
